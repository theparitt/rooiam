# Rooiam 0.3 — Sensitive Identity Action Approval

Updated: 2026-09-23. **Planned; no action-approval API or implementation exists yet.** This is the next-milestone handoff under the [release roadmap](./release_roadmap.md) and [product policy](./product_policy.md). The API names/model below are design targets, not current integration instructions.

## Product outcome and first journey

A workspace can require its administrator to confirm **creation of a workspace API key** on an enrolled phone. Approval confirms the exact operation the administrator is already permitted to perform. It never grants a role, substitutes for RBAC, or creates a login session.

1. An authenticated workspace administrator enters a key label, permission preset and expiry in the existing tenant portal.
2. When workspace policy requires phone confirmation, the server validates permission and saves an immutable action request. No key is created yet.
3. The portal shows its QR/request number. The phone displays the trusted Rooiam origin, workspace, action, requested permissions and expiry.
4. The same user explicitly approves or denies using an eligible enrolled device.
5. The initiating browser submits the original operation with its bound approval reference. The server rechecks authorization/policy and atomically creates one key and consumes the approval.
6. The portal displays the raw API key once, following the existing key-creation behavior. The phone never receives that key.

## Scope boundaries

**In 0.3:** one first-party action (`workspace.api_key.create`), one requesting/approving identity, explicit workspace policy, request preview/approve/deny/cancel/expiry, atomic execution, audit, Android SDK/reference support and portal UX. Add an extensible action registry, but register only the proven operation initially.

**Later candidates:** email change, trusted-device enrollment and other identity administration, each with its own threat model and acceptance. They are not automatically included in 0.3.

**Excluded:** payment/deployment/business workflows, arbitrary user-supplied actions, delegation/multiple approvers, a policy DSL, push delivery, iOS delivery, password reset/change features, general external approval grants and mandatory Rust SDK work. Rooiam remains passwordless IAM. Downstream apps continue to own business authorization/execution.

## Protocol decisions to implement

### Identity, purpose and immutable content

Use a separate action-approval purpose and versioned signing domain. **Never accept a device-login-v1 signature as action approval, or vice versa.** Login v1 routes, QR format, states, browser binding and existing clients keep their behavior. Unknown purposes/versions fail closed; old Android clients must safely reject a new action QR, not interpret it as login.

Proposed request records contain: random request ID, protocol/purpose version, requester user and session, workspace, fixed first-party audience, allowlisted action, resource identity/version, canonical normalized parameters and digest, policy version, nonce hash, created/expiry times, state, approving device, decision time and resulting object ID. For key creation, bind the workspace/key collection and the complete proposed key configuration because a new key has no resource ID yet.

The server derives identity/workspace/audience from authenticated context, validates the preset and derives actual permissions. Bind label, effective permission set, preset and expiry after normalization. Freeze them before review; any change needs a new request. Do not sign arbitrary JSON serialization. Task 03-01 must specify canonical bytes, domain separation, maximum lengths, expiry and fixtures before implementation.

The trusted phone fetches authoritative details from its enrolled origin. The server derives critical display fields from the frozen action; caller-provided labels cannot impersonate server metadata. Use bounded plain text, never supplied HTML. QR data contains only the trusted origin, purpose/version and opaque request reference—no session, signing key, API key or reusable approval secret. Keep the browser proof out of the QR.

### Routes and credentials

Proposed authenticated resource: `/v1/identity/action-approvals` (final schema frozen in 03-01): create/status/cancel for the requester; trusted-device preview/approve/deny for the same user. Bind requester calls to the original session, workspace, request and browser proof. Another session for the same user is not automatically authorized to consume it. Protect cookie mutations with the existing origin/CSRF controls and independently scoped rate limits.

The existing API-key create route becomes the only execution point for this pilot. A required approval reference is validated there; a caller cannot bypass policy by invoking the old route directly. There is no public generic execute endpoint and no bearer grant for unrelated applications. Workspace API keys cannot approve their own creation. Exact HTTP errors, binding fields and SDK methods remain proposed until 03-01; do not publish fictional calls as supported APIs.

### State and atomic execution

State target: `pending → approved → consumed`; `pending → denied/cancelled`; effective expiry from pending/approved. Terminal decisions cannot reactivate. No `claimed` state without a documented need. Only a cryptographically valid, eligible same-user device may approve. Browsers observe status but cannot convert it into authority for a different action.

At execution, lock the request and relevant device/account/workspace authorization records; validate expiry, requester session, frozen payload, action/resource/audience, current device eligibility and current permissions. Device revocation or removal of the requester's role before execution must block it. Lock ordering must also cover concurrent role/policy changes; independent pre-transaction checks are insufficient.

Require policy consistency: a changed policy version invalidates the pending approval and requires a fresh request. Turning off the policy must not reinterpret a stale request as approved. A new operation may follow the new authorized policy, with an audit trail. An unavailable attestation provider or phone is not implicit permission to bypass required approval.

Consumption, API-key insertion and durable audit/outbox entry share one database transaction. Serialize per-workspace key-limit checks as needed; races must not exceed the existing limit. Rollback leaves no usable key and no false consumed result. Once committed, replay cannot create a second key. Do not store raw keys in approval records or logs.

Lost execution response: expose only the resulting key's non-secret identity/status to the authorized requester. Do not regenerate or replay its raw secret. The user can revoke the unseen key and start a new, separately approved operation. Device approval does not mean the operation executed; UI must distinguish those states.

### Policy, MFA and recovery

Reuse existing permission semantics; add a narrow explicit action-policy setting, separate from the phone **login-method** toggle. Disabling phone login must not silently disable required action approval. Define the platform limit and workspace requirement separately; impossible policy combinations fail closed and are explained before enablement.

Before enabling required approval, validate that eligible administrators and a documented recovery path exist. Preserve current MFA/recent-auth requirements. A recent login, magic link or email alone must not silently satisfy a required device approval. Do not advertise generic assurance/AAL levels.

03-01 must define who may enable/disable the policy, how downgrades are confirmed/audited and how lost-phone administration is recovered without an auth bypass. Baseline recovery is a prerequisite, not work postponed to 0.7. If a safe recovery/downgrade contract cannot be agreed, keep the feature behind an operator-disabled preview flag and do not ship mandatory enforcement.

## Required regression matrix

- Happy path creates exactly the reviewed key/preset/expiry in the correct workspace; secrets appear only in the initiating browser's one-time response.
- Wrong user, session, browser proof, client/audience, workspace, action, resource or modified parameters are rejected; approval of `workspace.api_key.create` cannot authorize email change/account deletion.
- Bad signature, wrong purpose/version, stale nonce, wrong number, revoked/ineligible device, inactive user/workspace and expiry cannot execute.
- Deny/cancel/expiry races versus approval, duplicate approvals and concurrent execution produce at most one effect; terminal states remain terminal.
- Revocation, membership/role change, policy change and full-access-preset restrictions are rechecked at execution; policy cannot be bypassed through the preexisting endpoint.
- Crash/DB failure before and after commit, lost HTTP response and replay have defined behavior; no extra key, leaked secret or false success.
- Android background/process death/offline recovery revalidates the request; it never silently repeats a decision.
- Logs/audit contain request/action/actor/workspace/device/result identifiers, not browser proofs, device tokens, private keys or raw API keys.
- Existing magic link, OAuth, passkeys, MFA, OIDC, refresh rotation, phone login v1, API-key revocation and policy-off key creation keep passing.

**Release exit:** one supported identity operation is proven end to end under the declared policy, with safe recovery and compatibility. Add another operation only after its own immutable payload, permission, execution and recovery contract is reviewed. A generic approval platform is not a 0.3 completion criterion.
