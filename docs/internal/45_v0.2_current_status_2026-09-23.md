## Executive status

## Complete foundation

These items exist in code and can be treated as implemented foundations:

- trusted-device register, list, push-token update and revoke endpoints
- hashed device tokens and registered Ed25519 public keys
- signed approval payload verification
- Android Play Integrity and Apple App Attest backend paths, configuration and policy gates
- browser start, bound status, cancel and single conditional consume endpoints
- authenticated phone preview, approve and reject endpoints
- short-lived PostgreSQL intents, number choices and display code
- tenant-level device-login gate and workspace/client redirect resolution
- MFA-aware completion and opaque-session creation path
- audit events for start, cancel, approve, reject, registration, push-token update and revocation
- endpoint and per-IP limits on all device-login and device-management routes
- OpenAPI annotations for 11 device-login/device-management paths

“Implemented foundation” does not mean these items have passed real-device, vendor-service, live-database or adversarial release certification.

## Partial or unverified work

### Contract freeze

The mobile contract documents current payloads, but Phase A remains open. Decisions are still required for trusted server-origin handling, QR relay/substitution, terminal-state expiry representation, approved-but-abandoned requests, Android protected Ed25519 storage and protocol-version compatibility.

### Database and exactly-once behavior

Repository updates guard `pending → approved/rejected/cancelled` and `approved → consumed` with conditional SQL. This is a good atomic foundation. The audit did not run the three ignored PostgreSQL roundtrip tests because no test `DATABASE_URL` was supplied, and no mixed concurrency/failure matrix exists.

The highest-priority correctness risk is completion ordering: `complete_device_login` consumes the intent before `build_device_login_completion_response` resolves policy, creates MFA state, or creates the session. A downstream database/policy/session failure can leave an intent consumed without a usable completion response. Tests must establish the intended recovery behavior before alpha.

### Attestation

Vendor verifier paths exist, so older text saying “full platform attestation verification is not implemented” is too broad. What is missing is live proof with real Android/iOS clients, real vendor configuration and recorded failure/retry behavior. Compatibility verification and vendor verification must remain distinct in claims and release evidence.

### SDK contract

The TypeScript packages and generation pipeline are real and their local unit suites pass. Device-login support is not integrated into the SDK snapshot. The committed snapshot must be regenerated from the current 88-operation server spec, both schemas regenerated, and an automated drift check added before ergonomic device helpers are designed.
