# Rooiam 0.2 — Implementation Plan

Status: active milestone; Phase A is the current gate. Updated: 2026-09-23.

This replaces the previous SDK-only 0.2 brief. The [public roadmap](../roadmap.md) defines the release goal and acceptance criteria. Follow [product policy](./product_policy.md): self-hosted passwordless IAM for multi-tenant SaaS.

## Goal and baseline

**Scan. Match. Approve.** Deliver one verified Android-to-browser login journey using the existing identity platform. The vertical slice is implemented locally; real-phone and release certification remain open.

Keep the current layout: `rooiam-server`, `rooiam-app`, `rooiam-admin`, `rooiam-sdk/packages/js-browser`, `rooiam-sdk/packages/js-server`, and `rooiam-examples`. `rooiam-android` now contains the Phase C preview. No crate/workspace reorganization is required for this milestone.

Source baseline:

- `rooiam-server/src/modules/device_login/{models,service,repository,handlers,tests}.rs`: PostgreSQL intents, trusted devices, decisions and completion.
- `rooiam-server/src/modules/device_login/{google_play,apple_app_attest}.rs`: vendor attestation paths and their policy dependencies.
- `rooiam-server/src/openapi.rs` and `rooiam-sdk/spec/openapi.json`: API contract and SDK inputs.
- [Mobile contract](./44_mobile_device_login_contract.md): current request bodies and signing bytes.
- [SDK reference](../reference/13_sdk_and_device_login.md): current integration boundaries.

Existing implementations and unit tests are a baseline to verify, not proof of full release readiness.

## Immediate next work

Android delivery is now SDK-first: `rooiam-android/sdk` is the library and `rooiam-android/app` is its reference consumer. Integrators own camera/login UX, app lifecycle, signing/distribution and their Play Integrity project; Rooiam owns protocol/key handling and server verification. Protected installation of the reference APK is a reference distribution gate, not a prerequisite for library release. Vendor integration and independent SDK-consumer evidence remain required where claimed. See the [integration guide](../../rooiam-android/sdk/README.md).

1. Complete background/process-death review recovery, offline/MFA and hardware/Keystore scenarios; track reference-app protected installation separately using the Play Protect triage. Physical camera scan, approval and continuous client-bound callback pass on alpha.2 and the SDK-based alpha.3 reference app, including preservation of the existing enrollment after upgrade; logout also passes Chromium/API regression. Complete the independent SDK integration walkthrough separately.
2. Configure and verify real Play Integrity for the release package/distribution.
3. Complete browser UI, tenant/client, restart/disconnect, production-limit and log evidence.
4. Run the fresh-clone walkthrough and stable fuzz/1,000-flow gates. Check acceptance items only when their required evidence exists.

## Adaptations to the supplied proposal

| Proposal | Current implementation | 0.2 decision |
|---|---|---|
| New `/v1/auth/transactions` and `/v1/devices` APIs | `/v1/auth/device-login/*` and `/v1/identity/me/devices` | Extend existing routes; do not introduce a parallel login engine |
| `CREATED → CLAIMED → APPROVED → CONSUMED` | `pending → approved → consumed`; rejection/cancellation from pending; effective expiry | Document existing transitions first. A claim state needs an explicit security benefit and migration |
| QR includes a scan secret | `rooiam://device-login?server=…&public_id=…` | Review interception/relay and origin substitution. A scan secret is a proposed protocol change, not an existing field |
| PKCE verifier + separate authorization code | Browser nonce hash and user-agent binding; `/complete` consumes the intent; downstream OIDC already uses PKCE | Review binding and completion guarantees. Do not describe the nonce as PKCE or invent a second token exchange |
| Three-digit matching code | Two-digit number choices (`10..99`) plus a separate six-digit display code | Keep exact current fields in clients. A UX/length change must update the contract, SDK and tests together |
| 120-second intent / 30-second grant | Configurable `device_login_expiry_minutes`, default five minutes; no separate device grant | Validate settings and expiry boundaries; new lifetimes require a documented decision |
| P-256 device identity in Android Keystore | Ed25519 device approval key and hashed device token | Resolve supported Android storage/signing before implementation; never silently change the server algorithm |
| Attestation entirely deferred | Server already gates approval through attestation verification | Preserve the gate and document vendor configuration and compatibility limitations |
| Rust SDK and repository rewrite required | Two TypeScript packages and existing test runners | Extend these first; Rust SDK is deferred until a real consumer needs it |

## Phase A — Freeze the supported contract

- [ ] Document every state transition, effective expiry, error, request field, signing byte sequence, retry behavior and protocol-version handling against the implementation.
- [x] Preserve rejected/cancelled/consumed as terminal after expiry; regression test passes.
- [x] Keep approved requests non-cancellable; document reload, lost response and abandoned approval recovery.
- [ ] Threat-model QR substitution/relay, stolen browser nonce, stolen device token, signature replay, cross-client/workspace confusion and malicious server URLs. Number matching is a human check, not a phishing-resistance guarantee.
- [x] Bind phone credentials to the enrolled origin; reject substitution, insecure production origins and automatic redirects. Parser tests pass; hardware walkthrough remains Phase C.
- [x] Specify API 26 minimum and Keystore AES-GCM wrapping of Ed25519 seed. Signing is in memory; hardware tests remain open.
- [x] Record preview protocol version and workspace schema upgrade; synchronize the mobile contract and OpenAPI.

Exit: a reviewed contract and executable test matrix. No new QR fields or fictional SDK calls in published integration instructions.

## Phase B — Device trust and one-time completion

- [ ] Reuse existing account authentication for enrollment; test authorization, invalid/duplicate keys, cross-user reuse, device persistence, reinstall and revocation.
- [ ] Test actual Android attestation policy and vendor configuration. Separate compatibility-mode evidence from vendor verification; explain external-service requirements for self-hosters.
- [ ] Validate registered workspace/client context and server-resolved callbacks at start and completion. Check membership, suspension, policy changes and MFA without allowing cross-tenant escalation.
- [x] Lock approving devices against concurrent revocation; test revocation after approval and document the committed-result cutoff.
- [x] Make consumption and session/MFA insertion transactional; test insert failures and mixed concurrent result creation, and document lost-response recovery.
- [ ] Exercise PostgreSQL conditional updates with concurrent requests, transaction rollback and server restart. Keep protocol/state logic independent of UI.
- [ ] Complete production-mode abuse evidence across all routes. Start/status limits passed locally; device routes retain explicit limits even in test mode, unlike some general scopes.
- [ ] Audit successes, denials, expiry, cancellation, invalid signatures and revocation. Redact browser nonces, device tokens, private keys, session/refresh tokens and any future scan secrets/grants.

Exit: live database and security tests pass; at most one completion result per intent and no policy bypass.

## Phase C — Android and hosted-login experience

- [ ] Android: authenticate an existing user, enroll, scan, validate issuer, preview context, match, sign the exact server payload, approve/deny, and revoke/re-enroll.
- [ ] Hosted login in `rooiam-app`: respect workspace policy; show QR, matching prompt, expiry and status; cancel and restart safely; finish through existing MFA/callback behavior.
- [ ] Make device management understandable to the account owner using existing list/revoke APIs. Keep platform operator and tenant responsibilities distinct.
- [ ] Never display login success before browser completion and required MFA succeed. Define polling/backoff, offline, timeout and reload behavior.
- [x] Add a real-signing fake-phone harness and verify the HTTP and Chromium journey. Hardware acceptance remains separate.

Exit: real Android/browser happy path plus denial, expiry, revocation, offline and MFA cases. No push delivery dependency.

## Phase E — Release evidence

Extend the existing Rust tests, `test/` Hurl/security scripts and SDK test commands; add a release runner only when it orchestrates real checks. There is no assumed `cargo xtask certify` command.

| Required scenario | Evidence / expected result |
|---|---|
| Valid enrolled Android + correct match | Exactly one completion; MFA still enforced |
| Bad signature, wrong number, wrong nonce, revoked device | No authentication |
| Expired, denied or cancelled intent; guessed ID/code alone | No authentication; no reactivation |
| Replayed scan, signature, approval or completion | Safe rejection/idempotence; no duplicate session |
| Mixed approve/deny/expiry/complete races (50 of each) | Consistent outcome; sessions created ≤ 1 |
| Two users/devices/browsers/workspaces/clients | No identity or context leakage |
| DB failure, retry, restart, disconnect after consume | Defined recovery; no duplicate or false success |
| QR/parser malformed input, oversized bodies, unsupported values | Safe errors, no panic; fuzz/property regressions |
| Secret fixtures in logs and audit records | No credential leakage |
| Production-mode abuse tests | Configured limits enforced |
| Fresh clone and real Android walkthrough | Recorded prerequisites and reproducible success |

Add property tests for no terminal reactivation, no completion without approval and at most one consume. Run a documented 1,000-flow isolation test before stable; record hardware, configuration and results. Measure latency without promising unmeasured p95 targets.

Certification records the commit, configuration, commands, real-device details, pass/fail results and any skipped coverage. Missing Android/vendor/live-server evidence blocks the relevant gate; unit tests alone cannot certify it. Stable release requires every public acceptance item and no unresolved critical security issue or authentication bypass.

## Release sequence

- `0.2.0-alpha.1`: contract decisions and server/device hardening gates.
- `0.2.0-alpha.2`: integrated Android and hosted-login preview.
- `0.2.0-beta.1`: TypeScript integration, reference demo and operator walkthrough.
- `0.2.0-rc.1`: complete release evidence and security regression results.
- `0.2.0`: all gates passed. Additional prereleases are allowed; no date or package version is changed by this plan.

After 0.2, prioritize tenant/operator confidence. iOS, push, Rust SDK and broader authorization use cases require their own scope decision; payment and application business rules remain outside Rooiam's identity boundary.
